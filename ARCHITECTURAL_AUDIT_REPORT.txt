```

═════════════════════════════════════════════════════════════════════

🔴 HIGH RISK
──────────────

1. Database Schema Changes

   • Adding new fields to extras JSON is invisible (code change only)
   • Zero downtime deployment tricky with state machine changes
```

## EXECUTIVE SUMMARY & FINDINGS

### Key Findings

**STRENGTHS** ✓
1. **Well-designed Invoice Model**: Kind/Rectificative pattern enables proper financial auditing
2. **Good Availability Validation**: Flexible rules-engine for capacity management
3. **Good Atomicity in Billing**: select_for_update() locks prevent race conditions
4. **Reasonable Separation of Apps**: Logical domain boundaries (mostly)
5. **Language Support**: Multi-language bookings well-integrated

**WEAKNESSES** ✗
1. **State Machine in Views**: 850+ lines orchestrating business logic, no database constraints
2. **JSONField for State**: extras field used for critical state, no schema, hard to query
3. **Circular Dependency**: bookings ↔ billing tight coupling, hard to refactor
4. **Cascade Deletes**: Experience/User deletion destroys booking history
5. **Hardcoded Business Rules**: Tax rate, lead time, cancel cutoff not configurable
6. **No Transaction Boundaries**: Booking acceptance not atomic with conversation/invoice creation

**RISKS** ⚠️
1. **Data Corruption**: Invalid booking states possible via direct DB update
2. **Data Loss**: CASCADE deletes destroy financial/audit records
3. **Race Conditions**: Conversation creation after booking save → orphaning possible
4. **Maintenance Burden**: Feature development slow (2-3 weeks per feature)
5. **Regulatory Risk**: No audit trail for decisions, GDPR/compliance gaps

**VERDICT**: Solid foundation with critical flaws. Refactoring required before scaling to 100K+ bookings.
